# MiniLeague Baseball

## Why and what

Historical baseball simulation powered by public historical statistics: pick two of 15 classic teams (1927–1982, real Lahman statistics), manage the game, and watch it play out in a Classic (overhead) or Detailed (animated, behind home plate) view. It can be cast to a TV (Presentation API, `/tv` page). Standalone Blazor WebAssembly PWA, no server and no database; deployed as a static site.

**Stack:** .NET 10 (`net10.0`, Nullable on), Blazor WebAssembly, MudBlazor 9.1.0, plain JavaScript in `wwwroot/js` (canvas animator, synthesized sound), xUnit 2.9.3, bUnit 2.11.3, Playwright for .NET 1.65.1, Node's built-in test runner, Python 3 (data tool only).

**Map**
- `src/MiniLeague.Engine/` — the game: `Models`, `Simulation`, `AI` (computer manager), `Services` (game flow, save format, box score, recap), `Animation` (turns a play into a script). Plain class library, no package references.
- `src/MiniLeague.Web/` — the app: `Pages` (`GameRoom`, `Tv`, `About`, `Index`, `ShortcutCards`), `Components/Game` and `Components/Cast`, `Services`, `Shared` (layouts), `wwwroot/{data,js,css,images,icons}`.
- `src/MiniLeague.Web/wwwroot/data/` — team and ballpark JSON plus `ATTRIBUTION.md`; generated by `tools/generate_teams.py` from the Lahman database.
- `tests/MiniLeague.Engine.Tests/` (xUnit), `tests/MiniLeague.Web.Tests/` (bUnit), `tests/MiniLeague.Web.E2E/` (Playwright), `tests/js/` (Node tests).
- `.github/workflows/` — `pages.yml` (GitHub Pages) and `deploy.yml` (Azure Static Web Apps), both on push to `main`; `browser-tests.yml` (non-blocking).
- `docs/` — `AnimatedPlays.md` (animation spec), `chromecast-support.md`, screenshots.

## How to work

Needs the .NET 10 SDK (CI uses `10.0.x`). Node 20+ only for the JS tests; Python 3 only to regenerate team data.

```bash
dotnet restore MiniLeagueBaseball.slnx

# Dev server. --environment Development is required: without it static assets 404.
dotnet run --project src/MiniLeague.Web --no-launch-profile -- --urls http://localhost:5248 --environment Development

# Build = typecheck. Keep it at 0 warnings.
dotnet build MiniLeagueBaseball.slnx

# Tests
dotnet test MiniLeagueBaseball.slnx          # engine (xUnit) + web (bUnit)
node --test tests/js/sound.test.js tests/js/pwa.test.js tests/js/animator.test.js tests/js/cast.test.js
dotnet test tests/MiniLeague.Web.E2E         # Playwright in the installed Chrome, ~6 min
dotnet test <project> --no-build --filter "FullyQualifiedName~TestName"   # one test

# What CI publishes
dotnet publish src/MiniLeague.Web -c Release -o publish

# Regenerate team data (needs the Lahman CSV files)
python tools/generate_teams.py <folder with the Lahman CSVs>
```

- **Lint/format:** none configured (no `.editorconfig`, analyzers, ESLint or Prettier). Do not add one unasked; match the surrounding code.
- Engine tests read `wwwroot/data` by a path relative to the repo root: run them from a checkout.
- Do not run two `dotnet` builds at once. If a solution-wide build or test hangs, run one project at a time with `-m:1 -nodeReuse:false`.
- E2E: `AppFixture` runs `dotnet run --no-build` on a free port (building the E2E project builds Web first). `E2E_BROWSER_CHANNEL` picks another browser (`bundled` = Playwright's Chromium, needs `playwright install`).
- Comment style for new code is in `.claude/CLAUDE.md` (`// WHY:`, `// NOTE:`, `// HACK:`).

## Hard rules and stop conditions

**Git and releases**
- `main` is releases only, and every push to `main` deploys the site. Work on a feature branch.
- Do not commit unless asked. When asked: stage files by name (never `git add -A`), check `git status`, pass the message through a heredoc, and do not bundle unrelated working-tree changes under one message.
- Version = `<Version>` in **both** `MiniLeague.Web.csproj` and `MiniLeague.Engine.csproj`; a test fails if they differ. The owner names the number (feature release = minor, fix to `main` = patch). The menu footer and About page show it.

**Code**
- The engine stays a plain class library: no package or project references, nothing about the UI, the browser or JS.
- Adding a service that `GameRoom` or `MainLayout` injects means registering it in every bUnit fixture that renders them (`GameRoomTests`, `DetailedViewTests`, `PwaTests`, `ShortcutTests`), or those tests fail on a missing service.
- bUnit classes implement `IAsyncLifetime` and dispose asynchronously (MudBlazor). `MudBlazor.Position` clashes with `MiniLeague.Engine.Models.Position`: alias it.
- Browser tests wait on app state (locators, `mlbAnimator.playing`), never fixed sleeps. Dialogs do not close on Escape: use `GamePage.CloseDialogAsync()`.
- The E2E project is deliberately not in the `.slnx` (slow). `.gitignore` has a `*.e2e` pattern that would match its folder; the exception for `tests/MiniLeague.Web.E2E/` must stay.
- `MiniLeague.Web.csproj` needs both `<ServiceWorkerAssetsManifest>` and the `<ServiceWorker>` item, or publish silently ships the dev stub of the service worker.
- `wwwroot/index.html` share tags use absolute `https://` addresses and an image under 300 KB; `ShareTests` guards them.

**Data and legal**
- Statistics come from the Lahman database (CC BY-SA); ballpark distances are hand-entered and approximate. Keep the disclaimer and Lahman credit in step across `Pages/About.razor`, the README ("Data, credits and disclaimer") and `wwwroot/data/ATTRIBUTION.md`.
- No MLB, team or league logos or marks, and no "MLB" or "Major League Baseball" in names, domains or promotion.

**UI work**
- Run the app and look at it in a real browser (screenshot) before calling a UI change done. Believe the owner's reports of what they saw; find the cause instead of explaining it away.

**Stop and ask before**
- pushing, merging to `main`, tagging or releasing, or choosing a version number;
- editing `.github/workflows/*` or any deployment configuration;
- deleting or restoring files in `docs/` (the owner removed the original PDF and binary analysis; do not bring them back unasked);
- changing the disclaimer, attribution or license wording;
- any destructive git operation (reset, force-push, deleting a branch).

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.
